# CTO execution plan and prioritized backlog

2026-09-21 — initial offline delivery. **M0 discovery is partial; M1–M5 are not accepted.** The Chinese draft defines the requirements reference; the current task limits this work to read-only discovery, planning and a runnable offline foundation. Its rough schedule remains provisional and starts only when equipment, owners and decision gates are ready.

MVP acquisition gate: two actual cameras at validated ROI/pixel format, 100 fps from a shared per-frame hardware trigger, matching TDT recorded events, ≥30 minutes, zero unexpected dropped frames, and every gap/ambiguity reported. The document also expects camera previews/status and permits Synapse's native neural window alongside an interim interface. Final acceptance requires all experimental cameras for PI-defined duration and neural traces inside the unified application. Playback fps never establishes acquisition fps.

Original estimates: M0 2–3 days; M1 3–5 days; M2 about 1 week; M3 about 1 week; M4 1–2 weeks; M5 3–5 days. These are planning placeholders, not a delivery commitment. Hardware acceptance is sequential; schemas, offline QC and UI mock development can proceed while physical gates are blocked.

Decision gates:

1. **Timing evidence:** per-frame hardware IDs/ticks plus independently measured exposure/edge relationships. Calibrated clock mappings must identify source/target domain, fit/residuals, validity interval, resets/wrap handling and uncertainty. If repeated pulses leave multiple plausible associations, emit ambiguity; do not choose the nearest/order-based match without validated evidence. A source software log alone does not prove exposure.
2. **Recording:** native TDT files remain the neural authority. Session manifest must bind the actual tank/block, channels/stores, sample rates, exact camera configuration, wiring revision, software versions, writer segment indexes and calibration evidence. Leave unavailable fields empty. Future video tests must count actual decoded images, not container duration × nominal fps.
3. **Architecture:** compare Bonsai+pylon and a dedicated pylon service with identical real-device tests: metadata completeness, serial binding, queue control, dropped-frame detection, throughput, recovery and preview isolation. Select only after those results. Node is an offline harness choice, not the production camera/UI decision.
4. **Neural preview:** prove read-only channel access on the actual installation with measured latency/load. A control/status API is not automatically a raw waveform-streaming API. Use the allowed Synapse side-by-side fallback only as an interim arrangement; final in-app traces remain required.

Official documentation checked on 2026-09-21: Basler's [triggered acquisition guide](https://docs.baslerweb.com/triggered-image-acquisition) describes model-dependent trigger configuration and rate limits; its [timestamp guide](https://docs.baslerweb.com/timestamp) documents device ticks and model-specific frequencies. These do not validate the local configuration or authorize pin assignments. TDT's [SynapseAPI overview](https://www.tdt.com/docs/sdk/synapse-api/overview/) describes HTTP-based control/status and native Tank access; [mode-control documentation](https://www.tdt.com/docs/sdk/synapse-api/mode-control/) documents Record mode. No API call was made to local Synapse. [APIStreamer documentation](https://www.tdt.com/docs/sdk/online-control-and-data-analysis/apistreamer/) says bundled custom gizmos arrive in v96+, and buffer access competes with Synapse. With local v95, supported preview options require investigation; this is not proof streaming is impossible. Exact electrical claims remain deferred until model manuals are obtained.

Current blockers: recording-host identity, camera inventory/serials, TDT processor and event route, Doric chain, signed wiring, USB/storage evidence and PI thresholds. No hardware stage advances on simulator evidence.
